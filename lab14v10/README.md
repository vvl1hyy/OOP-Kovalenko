## Аналіз принципів SRP та OCP

### 1. Приклади вдалого застосування SRP
* **Репозиторій:** `Newtonsoft.Json`
* **Файл/Клас:** `Newtonsoft.Json/Serialization/DefaultContractResolver.cs`
* **Аналіз:** Клас відповідає виключно за створення контрактів серіалізації для типів .NET (визначення того, які властивості та поля будуть серіалізовані). Він не займається парсингом рядків чи записом у стірим. Це полегшує підтримку: зміна логіки відображення властивостей ніяк не впливає на сам механізм читання JSON.

* **Репозиторій:** `MediatR`
* **Файл/Клас:** `MediatR/Mediator.cs`
* **Аналіз:** Клас відповідає виключно за координацію та диспетчеризацію запитів до відповідних обробників (`IRequestHandler`). Він делегує процес виконання спеціалізованим хендлерам, дотримуючись єдиної відповідальності за маршрутизацію викликів.

---

### 2. Приклади порушення SRP
* **Репозиторій:** `Newtonsoft.Json` (класи ранніх версій / внутрішні утиліти)
* **Файл/Клас:** `Newtonsoft.Json/Utilities/ConvertUtils.cs`
* **Аналіз:** Статичний клас бере на себе одночасно конвертацію типів, перевірку на нулли, роботу з рефлексією та форматування дат. Якщо змінюються правила приведення типів або логіка роботи з рефлексією, цей файл доводиться часто модифікувати, що створює ризик появи побічних ефектів у різних частинах бібліотеки.

---

### 3. Приклади розширення за OCP (плагіни / стратегії / абстракції)
* **Репозиторій:** `Newtonsoft.Json`
* **Файл/Клас:** `Newtonsoft.Json/JsonConverter.cs`
* **Аналіз:** Абстрактний клас `JsonConverter` дозволяє розширювати поведінку серіалізації для кастомних типів без модифікації вихідного коду самого парсера. Щоб додати підтримку нового типу даних, розробник створює новий клас-нащадок і реєструє його, що є класичним дотриманням OCP (відкрито для розширення, закрито для модифікації).

* **Репозиторій:** `MediatR`
* **Файл/Клас:** `MediatR/Pipeline/StreamPipelineBehavior.cs` (або пайплайни поведінки `IPipelineBehavior`)
* **Аналіз:** Система патерну поведінки дозволяє додавати нову скрізну логіку (логування, валідацію, кешування) через створення нових класів, які реалізують інтерфейс `IPipelineBehavior`, не чіпаючи базовий код відправки повідомлень.

## Висновки
Аналіз відкритих репозиторіїв на базі .NET показує, що дотримання принципів SOLID є критичним для забезпечення масштабованості та стабільності бібліотек з великою кількістю користувачів. Дотримання SRP дозволяє локалізувати зміни та уникнути "спагеті-коду", коли один компонент відповідає за все навколо. Успішна реалізація OCP через абстракції (інтерфейси та віртуальні методи) дає змогу стороннім розробникам легко інтегрувати власні плагіни та розширення без потреби переписувати ядро бібліотеки. Водночас наявність допоміжних утиліт із занадто широким спектром завдань підтверджує складність повного дотримання чистоти архітектури в історично станах проєктів.

## Пропозиція рефакторингу для класу-утиліти (`ConvertUtils`)
Для усунення порушень SRP утилітарних класів перетворення типів доцільно застосувати шаблон проєктування **Strategy** або розділити статичний монолітний клас на окремі дрібні сервіси (наприклад, `TypeConverter`, `ReflectionHelper`, `DateFormatter`), кожен з яких відповідатиме лише за один конкретний аспект перетворення даних. Це зменшить зв'язність коду (coupling) та спростить модульне тестування.
